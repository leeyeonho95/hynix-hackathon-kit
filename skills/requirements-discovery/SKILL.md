# 요구사항 끌어내기

현업 담당자는 할 일 목록을 한 번에 주지 않는다. 작은 맥락 질문에서 시작해 깊은 질문으로 좁혀 간다.

## 1. README 분석 (코드 수정 없이)
아래 표를 채워서 사용자에게 보여준다.

| 항목 | README에 있음 | 모름(질문 필요) |
|---|---|---|
| 누가 쓰나 (사용자/역할) | | |
| 지금은 어떻게 하고 있나 (현재 업무 흐름) | | |
| 무엇이 불편한가 (페인포인트) | | |
| 입력 데이터 / 출력 형태 | | |
| 성공 기준 (무엇이 되면 끝인가) | | |
| 제약 (기술, 시간, 형식) | | |

## 2. 질문 설계 원칙
- 넓은 질문 하나로 "다 알려 달라"고 하지 않는다. 하나씩 묻는다.
- 순서: 맥락 → 현재 흐름 → 불편함 → 예외 상황 → 우선순위 → 성공 기준.
- 질문마다 "이 답이 설계의 무엇을 바꾸는지"를 사용자에게 함께 적어 준다.
- 예시
  - "이 일은 보통 누가, 얼마나 자주 하세요?"
  - "지금은 어떤 도구로 처리하시고, 어디서 시간이 제일 많이 드세요?"
  - "가장 곤란했던 실제 사례 하나만 말씀해 주실 수 있을까요?"
  - "이게 잘 됐다고 판단하시는 기준은 뭔가요?"
  - "반드시 있어야 하는 것과 있으면 좋은 것을 나눈다면요?"

## 3. 답변 정리
답을 받을 때마다 `REQUIREMENTS.md`를 갱신한다.

```
## 사용자 / 맥락
## 핵심 문제
## 기능 요구사항 (Must / Should / Won't)
- [M1] ... — 근거: 담당자 답변 "..."
## 인수 기준 (검증 가능한 문장)
- M1: 사용자가 X를 하면 Y가 Z초 안에 보인다
## 아직 모르는 것
```

- 근거 없는 요구사항은 `가정:`으로 표시한다.
- Won't(이번에 안 할 것)를 반드시 적는다. 과설계를 막는 장치다.
